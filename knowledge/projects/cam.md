# ai-cam 工业相机采集 · 项目说明

## 概况
- 个人作品集项目，由我一个人完成。演示：http://47.117.29.74:8098/ ；源码：https://github.com/rfs151/ai-cam
- 做什么：工业相机（GigE Vision / USB3 Vision）采集链路的完整示例：设备 SDK 接入、触发、帧号与时间戳、帧池与有界队列、异步写盘、状态机与断线重连、录像校验、分层丢帧统计。没有真实相机时用 Aravis 虚拟 GigE 相机、海康虚拟相机或内置模拟相机运行。
- 和我工作经历的关系：对应求职方向里的机器视觉；多线程、内存与性能优化是我长期做 C/C++ 系统开发积累的能力。

## 架构
- C++17 采集引擎 capd：取帧线程只拷贝和归还缓冲 → 帧池取缓冲 → try_push 到有界队列（64）→ 写盘线程校验帧号、CRC、fwrite、滚动文件；状态机线程负责断开 → 连接 → 配置 → 采集 → 出错 → 退避重连；统计线程每秒输出 fps、MB/s、队列水位、丢帧。预览用 libjpeg 编码。
- web/api（FastAPI）通过 stdin 命令 / stdout JSON 控制 capd，WebSocket 把状态、统计和 JPEG 预览推给浏览器。

## 高帧率下的并发设计
- **采集线程永不阻塞**：队列满时直接丢弃并计数，而不是等待；否则相机 / SDK 内部缓存溢出，丢得更多且不可控。
- **帧池**：高帧率下每帧 new 几 MB 会造成内存碎片和延迟抖动；池子耗尽本身就是"下游积压"的信号。
- **SDK 缓冲及时归还**（arv_stream_push_buffer / MV_CC_FreeImageBuffer）：回调或取帧线程里只拷贝，不做算法和 I/O。
- **断线重连**：异常回调只置标志，由状态机线程释放资源并指数退避重连；重连后帧号可能从 0 开始，写盘侧记录"会话号"区分。
- 带宽估算：2048×1536 Mono8 @200fps ≈ 630 MB/s，超过千兆网（约 110 MB/s），需要万兆、ROI/Binning 或 USB3/CoaXPress，写盘需要 NVMe 或 RAID。

## 难点与解决
- **定位是哪一层在丢帧**：网络包 → 拼帧 → SDK 缓冲 → 帧号 → 程序队列 → 文件，六层分别计数，页面实时显示，并自动给出诊断，比如"每帧 193 个包，完整帧概率 (1−p)^n ≈ …"。分开统计才能判断瓶颈在相机、网络还是磁盘。
- **丢包对完整帧的影响**：512×512 每帧 193 个包，丢包 2% 时完整帧几乎为 0（0.98¹⁹³ ≈ 2%）；改用 8000 字节巨帧后每帧 132 个包，完整帧回到约 7%。
- **断线恢复**：2 秒内发现掉线，按 100 ms → 5 s 指数退避重连，相机恢复后约 1 秒继续采集并重新下发参数。
- **数据可校验**：录像每帧 48 字节帧头 + CRC32；慢磁盘录 8 秒时队列丢 81 帧，离线校验报告缺约 80 帧，两边对得上。
- **故障注入**：网页上一键拔网线、设置丢包率 0～5%、让取帧线程或磁盘每帧额外耗时，观察采集端反应；还能看到 16 位帧号 65535 → 1 绕回。
- 公网演示同一时间只有一个人能操作（其他人旁观），3 分钟没有操作自动释放。

## 关键数据与技术栈
- 技术栈：C++17、GigE Vision、Aravis、GenICam、libjpeg、FastAPI、WebSocket、PyQt5。
- GigE 调优要点：巨帧 MTU 9000、增大网卡 ring buffer（ethtool -G）、增大 socket 接收缓冲（net.core.rmem_max）、采集线程绑核 / 提高优先级；时间戳用相机硬件时间戳，多相机用 PTP 同步。
