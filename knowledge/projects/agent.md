# 作品集 AI 助手（ai-agent）· 项目说明

## 概况
- 个人作品集项目，由我一个人完成：首页上替我回答招聘方问题的 AI 助手，也就是正在回答的这个助手。源码：https://github.com/rfs151/ai-agent
- 做什么：按我的简历和项目资料，用第一人称回答经历、项目、技术细节；贴职位描述（JD）会生成逐条匹配报告；要联系方式直接给出；查询演示是否在线、ai-vision 的实时运行数据；在页面上高亮相关项目卡片。

## 多 Agent 编排（LangGraph）
- 用 LangGraph 的 StateGraph 编排：记忆节点 → 路由 Agent → 三条分支（问答 Agent、JD 匹配工作流、联系方式）→ 保存会话。
- 路由 Agent：一次 JSON 模式的模型调用，判断意图（问经历 / JD 匹配 / 联系），同时记下对方说出的公司、岗位和关注点。
- 问答 Agent：工具调用循环，最多 5 步，最后一步不给工具，必须回答；工具并行执行。工具有知识库检索、演示在线状态、ai-vision 实时数据、页面高亮。
- JD 匹配工作流是固定流程：拆解 JD 成最多 8 条要求（必须 / 加分）→ 每条要求并行做混合检索（不调用模型）→ 一次 JSON 调用逐条打 0～3 分并引用证据编号 → 表格和匹配度由程序生成（必须项权重 2，加分项 1），模型只写差距和总结。表格由代码渲染，证据链接来自检索结果，减少编造。
- 联系方式分支不调用模型，留言功能暂不开放。

## RAG 知识库
- 内容：每个项目一篇我写的项目说明（架构、难点、我的贡献、并发与性能、关键数据），加各项目的 README 和设计文档，按标题切块（约 360 段）。
- 混合检索：BM25（中文两字切分，不需要分词库）+ 向量检索（bge-small-zh-v1.5，fastembed / ONNX Runtime 本地 CPU 推理，查询向量化约 5 ms），两路结果用 RRF（倒数排名融合）合并，页面上能看到每段结果是关键词还是语义检索命中的。
- 为什么要向量：问"你怎么解决高并发"时，文档里写的是"多路并发与性能""实时性与并发设计"，关键词不完全对得上，语义检索能找到；而"OpenVINO 绑核""mFRR"这类专有名词关键词检索更准。
- 文档向量离线生成（scripts/build_index.py），没有向量数据库：几百段，numpy 矩阵乘就够了。

## 记忆
- LangGraph 的 SQLite checkpointer 按会话保存状态（thread_id = 会话 id），服务重启后对话不丢。
- 最近的消息原样保留；对话变长后，记忆节点把较早的消息压缩成摘要。贴过的 JD 在历史里只存拆解后的要求，不存原文。
- 记住访客的公司、岗位和关注点，放进问答 Agent 的上下文，回答优先讲和这个岗位相关的经历。

## 工程细节
- 模型 DeepSeek（OpenAI 兼容接口），全部流式调用；SSE 把节点开始 / 结束、工具调用、文本增量、记忆更新、费用推给页面，每个回答可展开看执行路径、每步耗时、token 和费用。
- 费用：系统提示词（规则 + 简历 + 项目摘要）固定不变，放在最前面，问答 Agent 和 JD 打分 / 报告共用，命中 DeepSeek 前缀缓存；每个问题约 0.01～0.03 元。
- 防滥用：按 IP 和全站限流、每日费用上限、单条长度和会话轮数限制；用户消息和工具结果只当资料，防提示注入。
- 测试：pytest 用模拟的 DeepSeek 流式接口，覆盖路由三条分支、JD 工作流、记忆压缩、工具循环、限流和出错，测试不花钱。
- 技术栈：Python、FastAPI、LangGraph、DeepSeek、fastembed（bge-small-zh）、NumPy、SQLite、SSE、原生 JS。
